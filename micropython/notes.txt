Micropython isn't multithreaded - Python code doesn't run in parallel. How can we run the wifi-settings connection code, or the remote access service?
One method is to use asynchronous Python and provide a service which should be executed asynchronously during user code. This depends on the user code executing the command (but then, in C, we depend on the user calling an API function). It also assumes the user code doesn't do something that disrupts async execution (such as entering an infinite loop). The same is somewhat true in C, though C code would also have to disable interrupts to really close everything off. I don't think the Python code can do this. 
The appeal of this method is that it will be very portable to all Micropython devices. And remote access services can also be written in Python, and will have no difficulty doing anything that can be done in Python such as modifying files or even executing expressions. However, it would require a rewrite of wifi-settings in Python, and the limitations of the Micropython network API would be retained - for example scanning for APs is a blocking task.

I think that asyncio could work, but it would require the involvement of user code,
which would need to initialise wifi-settings while an asyncio event loop was running.
Or would it? could we start a task and then return?

One bad thing about asyncio is that we have to know the ip address in order to start_server.
I expect it would be necessary to start_server again if the network interface changed
e.g. new hotspot.

It is possible to do:
    loop = asyncio.get_event_loop()
    task = loop.create_task(asyncio.start_server(serve_callback, ip, port))

without actually doing asyncio.run(...) however the server won't actually start until
asyncio.run(...) is reached. So, buggy user code that doesn't reach "run" (or
crashes) will also prevent remote access. If "run" exits early then the socket will still
accept connections but serve_callback won't service them until "run" is called again.

I might be able to create a new event loop just for the server which is executed by a timer.
It would process all pending events. But the trouble is that most activities would have to wait
for the timer. The correct interrupt to use would be one associated with the network;
the tcp_recv and tcp_accept functions in LwIP are the correct ones.

Using the socket module - the trouble here is that I'd need to register a callback
somehow, to be called whenever a connection is accepted or data is received. This is not
normally a feature of the socket module...

The secret is to call lwip_socket_setsockopt with args[2] = 20 and args[3] = a callback function

Using socket.socket with the callback registration it is even possible to bind the
socket to "" before an IP address is obtained, indeed before even the wifi connection is available,
and this will still work!

Could this callback be used with asyncio to run through the loop on each event? Yes in principle,

UDP issue: pico-wifi-settings needs UDP in order to respond to searches for boards
by broadcast on port 1404. But this doesn't work on Micropython. Receiving a
UDP packet does not trigger any callback (registered with lwip_socket_setsockopt(20)).
The issue was already reported. https://github.com/micropython/micropython/issues/3594 .
I created a pull request. The problem is easily fixed but I don't know if the Micropython's
maintainers want to keep this method of handling packets. I thought it might be used
for asyncio but as far as I can tell, it isn't. I think asyncio's core might wait for TCP
packets by polling rather than the setsockopt(20) callback, possibly in core.run_until_complete,
which is possible for asyncio because one foreground task can block in a polling loop, but
it won't work for pico-wifi-settings which needs to run in the background.

On Micropython asyncio doesn't support UDP anyway, so I can't pivot to a completely
asyncio-based implementation of pico-wifi-settings, which in any case would bring
other problems as described above (user code would have to use asyncio properly and not
be blocked somehow, so pico-wifi-settings would be less useful for recovering from bugs).

The webrepl server seems to be the only official use case for setsockopt(20) and I suspect that the
maintainers might prefer a different and more general way to do it. The lack of an officially
#defined name for the magic number 20 is suspicious. Aside from UDP there are other cases where
a callback might be useful, for example tcp_error and tcp_ack.

Currently Micropython determines if an LwIP stream has data for reading, or space for writing,
by calling lwip_socket_ioctl with request = MP_STREAM_POLL. This seems to be the standard way
to determine if a "non-file-descriptor object" is ready for read/write - see
MICROPY_PY_SELECT_IOCTL_CALL_PERIOD_MS. I would guess that there might be interest in replacing
this with some kind of notification to avoid polling, and that would be more general, and
setsockopt(20) would be obsolete, and hence there would be little interest in propagating it now,
and thereby enabling programs and libraries which would cease to be compatible with Micropython
in the future.

so I am left with a few Micropython problems that I think cannot be solved without changes in
the main Micropython source code.

1. Searching for WiFi hotspots is a blocking operation, so the system becomes temporarily
   unusable. Users of Micropython have complained that getaddrinfo is blocking and that this
   is a nuisance when responsiveness is needed. A hotspot search is probably less bad (only local)
   but still bad.

2. There is no callback to show that a TCP connection has been closed or that an ACK has arrived,
   so pico-wifi-settings can't take actions after transfers complete. This could be worked around
   using machine.Timer - somewhat crudely, but perhaps well enough.

3. There is no callback to notify when a UDP packet arrives, so pico-wifi-settings can't respond
   to UDP broadcasts on port 1404 from remote_picotool. Again, machine.Timer could work around this
   by having a periodic task that receives UDP. Also I have submitted a bug fix. And also, are these
   UDP broadcasts really appropriate? There is also multicast DNS.

There are workarounds for problems 2 and 3, and at this point pico-wifi-settings
is able to respond to messages. It is not brilliant. bytes() is used everywhere, which is slow,
and it isn't able to do much, and it's barely tested. But a vertical slice has been implemented.

I know that multicast DNS requires UDP, so I was curious how it could work.
https://github.com/cbrand/micropython-mdns.git uses a 100ms periodic task to receive UDP packets,
so it's like the "machine.Timer" solution, though it uses asyncio. UDP support isn't in
Micropython's asyncio, so the code uses the socket module directly.

Should the C implementation of pico-wifi-settings be used here? I like the idea of reusing the
existing code and all three problems go away if LwIP and cyw43 functions can be called directly.
However Micropython would have to be rebuilt, there is no way to bring in the module in binary
form because it has to use lwip functions, and I doubt that such a large feature would be wanted
in the mainline Micropython. So I do still think that a C implementation is out. 

What features should pico-wifi-settings provide on Micropython? The basic features are
"remote_picotool info", "remote_picotool update" and "remote_picotool reboot", all of which
can be implemented.

Firmware updates are probably not feasible because these require storing the new firmware
somewhere temporarily, and then installing it, and the only available storage is the filesystem
since the Flash is fully used (first part firmware, second part filesystem). New firmware can be in
a file, but the installer would need to be able to decode the filesystem structure without calling
functions in Flash, and I think this is infeasible, since there are at least two supported filesystems
with an abstraction layer.

Updating the Python code is feasible; basically what's needed here is a feature like "mpremote cp"
which can copy files to the target system. At the moment pico-wifi-settings doesn't have support
for that because it makes no sense unless there is a filesystem.

Thinking about that idea, and the various other features of "mpremote", I wanted to ask if "mpremote"
could be adapted to communicate over the network
I found this related thing: https://github.com/micropython/micropython/pull/18633 
and I saw 
    mpremote connect socket://localhost:2218 eval "1+1"
given as an example. Actually this still uses serial communication, but "socket://" is recognised
by the pyserial module as a port, and it translates the communications to TCP/IP. Theoretically
the client side needs no changes. In reality, changes are needed, and PR 18633 incorporates these.
It seems like there are lots of small bug fixes. Perhaps some mpremote features won't work well.
The terminal feature is particularly concerning.

I looked at the SerialTransport class. It does look as if this could be replaced by a NetworkTransport
class - mpremote doesn't provide a plugin interface to help with this but mpremote could be modified
directly (forked). I think the basic ability is to be able to run a block of code as if typed into the
REPL. There is a special serial mode to allow large blocks to be sent ("raw paste"). Having sent a
command it waits for a result which is also a block.
